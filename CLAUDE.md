## Про проект

`cip_gov_ua_getter` — консольна утиліта для збору розпоряджень про блокування доменів.
Джерела — два сайти НЦУ: `cip.gov.ua` (розпорядження) і `webportal.nrada.gov.ua`
(перелік сервісів держави-агресора), а також `nkek.gov.ua` з рішеннями щодо
блокування «ПлейСіті». На виході — `blocked.result.txt` зі списком доменів
для блокування на рівні DNS.

Утиліта потрібна провайдерам для виконання розпорядження НКРЗІ про щоденний
моніторинг розпоряджень НЦУ.

**Кожен коміт із змінами коду повинен містити також:**

1. **`pom.xml`** — оновлену версію відповідно до Semantic Versioning:
   - нова фіча → мінорний реліз (1.17.x → 1.18.0)
   - виправлення / дрібне покращення → патч (1.17.0 → 1.17.1)
   - зламна зміна → мажорний реліз (1.x.y → 2.0.0)

2. **`CHANGELOG.md`** — новий розділ `## [X.Y.Z] — YYYY-MM-DD` з описом усіх змін
   (підрозділи: `### Додано`, `### Змінено`, `### Виправлено`)

3. **`README.md`** — оновлені розділи, що стосуються змінених функцій

4. **`CONTRIBUTING.md`** — оновлювати за необхідності

Це не опціонально. Якщо зміна коду є — документація оновлюється в тому самому коміті.

## Збірка та запуск

```bash
mvn clean package                                  # збірка uber-JAR
java -jar target/cip_gov_ua_getter-3.4.0-all.jar   # звичайний запуск
java -jar target/cip_gov_ua_getter-3.4.0-all.jar -d # дебаг-режим
```

Конфігурація — `cip.gov.ua.properties` у корені (шлях можна передати аргументом).
Логи — `logs/cip_gov_ua_getter.log`, налаштування у `src/main/resources/logback.xml`.

Тестів немає. Перевірка змін — реальний запуск і аналіз логів.

## Архітектура

Потік даних лінійний, точка входу — `Cip_gov_ua_getter.main()`:

1. `BlockedObjects.getBlockedDomainNames()` — читає базові списки доменів із файлів (`blocked`).
2. `CGUGetter` — через Playwright тягне JSON зі списком розпоряджень з API `cip.gov.ua`.
3. `ParseCGUArticlesJson` — дістає масив `posts`.
4. Для кожного поста: фільтр за `ban_keywords`/`unban_keywords` → для кожного вкладення
   `GetPrescript` завантажує/читає файл і валідує домени.
5. `AggressorServicesParser` (наслідує `AbstractPDFParser`) — парсить PDF з `nrada.gov.ua` (НЦУ).
6. `PlaycityParser` (наслідує `AbstractPDFParser`) — парсить рішення щодо «ПлейСіті» за списком `urlPdfs`.
7. `BlockedObjects.storeState()` — атомарно пише результат.

Уся валідація доменів зосереджена в `DomainValidatorUtil.validateDomain()` — спільній
для текстових розпоряджень і PDF.

## Ключові принципи, які треба зберігати

**Playwright, а не HTTP-клієнт.** `cip.gov.ua` має анти-бот захист; звичайний
`HttpURLConnection` отримує відмову. Тому запити йдуть через headless Chrome.
Не замінювати на простий HTTP-клієнт.

**Без паралелізації запитів до cip.gov.ua.** Між зверненнями стоїть пауза 1–2 с
(`Cip_gov_ua_getter`, після `!gp.isLocalRead()`). Паралельні запити ризикують
призвести до блокування. Паралелити можна лише локальну обробку (розбір PDF,
валідацію) або завантаження з інших доменів.

**Кешування обов'язкове — але не завжди назавжди.** Вкладення розпоряджень
(`store_prescript_to`) і рішення щодо «ПлейСіті» (`PlaycityParser`) —
незмінні історичні документи за унікальним ID/URL; їх кешування назавжди
коректне, не ламати перевірку `isExists()`. Перелік сервісів держави-агресора
(`AggressorServicesParser`, теж НЦУ) — принципово інший випадок: сайт nrada.gov.ua оновлює «поточний стан»
по-різному — інколи під новим іменем файлу, інколи вміст під тим самим, —
а локальний кеш зберігається під одним фіксованим іменем незалежно від
цього. Тому там кеш має термін придатності (`AggressorServices_max_age_hours`,
типово 24 год) через `downloadPdf(..., Duration maxAge)`: застарілий файл
намагається оновитися щоразу, а якщо сервер недоступний — використовується
наявна застаріла копія (WARN у лог), а не провал джерела. Без цього
розмежування перелік роками не оновлювався б, ігноруючи все, що nrada
публікує після першого успішного завантаження.

**Стійкість важливіша за швидке падіння.** Збій одного поста, вкладення чи PDF-парсера
не має зупиняти весь запуск: кожен такий блок обгорнуто в `try-catch`, помилки
пишуться у лог і `failed_ids.txt`, а `bo.storeState()` після них викликається завжди.
Єдиний свідомий виняток — повна відмова отримати сам перелік розпоряджень
(`CGUGetter`, після вичерпання повторів): тоді запуск переривається, а
`storeState()` **не** викликається, щоб неповний результат не перезаписав
робочий `blocked.result.txt`. Див. `Cip_gov_ua_getter.main()`.

**Атомарний запис — скрізь, де щось зберігається.** `blocked.result.txt`,
завантажені PDF і кешовані вкладення пишуться через тимчасовий файл +
`Files.move(ATOMIC_MOVE)` з фолбеком на `REPLACE_EXISTING`. Логіка зібрана в
`AtomicFiles` — не дублювати її і не повертатися до прямого запису в цільовий
файл. Причина не лише в паралельності: обірваний запис лишає частковий файл,
який `isExists()` вважає валідним кешем, і зіпсована копія використовується
роками (саме так утворився інцидент зі застарілим переліком агресора).

**Завантажене треба перевіряти.** PDF валідується за сигнатурою `%PDF-`
(`requirePdfSignature`) до того, як потрапить у кеш: сервер може віддати
HTML-сторінку помилки з кодом 200, і без перевірки вона осяде під іменем
`.pdf` та «парситиметься» щоразу.

**SSL — per-connection і тільки для дозволених хостів.** `webportal.nrada.gov.ua`
має некоректний ланцюжок сертифікатів. Обхід реалізовано через
`createTrustAllSslSocketFactory()`, що застосовується лише до конкретного
з'єднання після `SSLException` **і лише якщо хост є в `ssl_bypass_hosts`**
(типово тільки nrada). Без цього обмеження активний MITM міг би навмисно
зірвати рукостискання на будь-якому джерелі, дочекатися повторної спроби вже
без перевірки й підсунути власний перелік доменів — а він іде прямо в DNS
провайдера. **Ніколи** не повертати глобальний
`HttpsURLConnection.setDefaultSSLSocketFactory()` і не знімати перевірку хоста.

**Публічний суфікс — не домен.** `DomainValidatorUtil` ніколи не віддає імена
на кшталт `com.ua`, `kiev.ua`, `co.uk`: заблокувати такий запис на DNS означає
покласти цілу зону. Тому службовий субдомен зрізається лише тоді, коли після
цього лишається реєстрований домен (перевірка через `InternetDomainName` з
Public Suffix List), а сам публічний суфікс відкидається з WARN. Імена
на кшталт `shop.com.ua` — цілком законні цілі блокування й лишаються як є.

**`prepareDocument` прибирає `\n`, а не замінює на пробіл. Не «виправляти».**
Це питання вже досліджували на реальному «Переліку» НЦУ — не починати заново.
Спокуса очевидна: після видалення переносу кінець одного запису злипається з
початком наступного (`hd.muvee.me` + `https://…` → `hd.muvee.mehttps`), і
заміна на пробіл виглядає як загальне вирішення. Але PDF-редактор так само
переносить рядок **посеред** доменного імені, і тоді пробіл робить одразу дві
біди. У тому самому документі є `https://hdplayer.kinogo-\nnew.com`: із
пробілом справжній домен `hdplayer.kinogo-new.com` розсипається на сміття, а
з хвоста народжується `new.com` — домен, якого в джерелі немає, але який
успішно проходить валідацію й пішов би прямо в DNS-блокування провайдера.
Перевірено експериментально. Втратити справжній домен погано, вигадати
неіснуючий — гірше, тому стратегія лишається як є, а склеювання лікуються
евристичними фолбеками в `DomainValidatorUtil` (склеєна схема наступного
URL, склеєний номер наступного рядка таблиці). Кожен фолбек спрацьовує лише
**після** невдачі звичайної валідації й перевалідовує відновленого кандидата
повним ланцюжком перевірок — тож зробити гірше, ніж «нічого не робити», він
не може.

**Один авторитетний прохід + один дорадчий, і вони не змішуються.** Оскільки
жодна стратегія об'єднання рядків не є правильною завжди, друга (перенос →
пробіл) живе окремо: `AbstractPDFParser.reportPossiblyMissedDomains()`
проганяє той самий текст ще раз і виписує різницю з основним результатом у
`possible_missed_domains.txt`. Це **пропозиції людині**, а не блокування — в
`blocked.result.txt` вони не потрапляють ніколи, і цю межу не розмивати.
Файл читається-доповнюється-переписується під `synchronized` (PDF
розбираються паралельно) і атомарно, тож дублів у ньому не буває; заглушити
конкретну пропозицію назавжди можна через `possible_missed_domains.ignore`.
Дорадчий прохід логує на `DEBUG` (прапорець `quiet` у `validateDomain`) —
інакше він подвоював би INFO/WARN-логи, дублюючи те, що вже сказав
авторитетний прохід.

## Конфігурація

Ключові властивості `cip.gov.ua.properties`:

| Властивість | Призначення |
|---|---|
| `urlArticles` | API зі списком розпоряджень |
| `urlPrescript` | Префікс URL для завантаження вкладення (додається `id`) |
| `blocked` | Вхідні файли з доменами, через `;` |
| `blocked_result` | Вихідний файл |
| `store_prescript_to` | Кеш вкладень |
| `urlAggressorServices` | Сторінка НЦУ з переліком сервісів агресора |
| `AggressorServices_max_age_hours` | Термін придатності кешу PDF агресора, у годинах (типово 24) |
| `urlPdfs` | PDF рішень щодо «ПлейСіті»: прямі URL через кому **або** `file:/шлях/до/списку` |
| `ban_keywords` / `unban_keywords` | Регулярні вирази через `\|` для фільтра постів |
| `max_file_size_bytes` | Ліміт розміру вкладення |
| `ssl_bypass_hosts` | Хости, де дозволено обхід перевірки TLS, через кому (типово лише `webportal.nrada.gov.ua`) |

Файл читається як UTF-8 через `InputStreamReader`, але кирилиця може бути збережена
IDE як `\uXXXX` — обидва варіанти працюють.

Для `urlPdfs` із префіксом `file:`: у файлі один URL на рядок, рядки з `#` —
коментарі, `~` розгортається в домашню директорію. Відсутній файл → `WARN`, не падіння.
